# SkimmerSense v0.9 firmware plan

This branch prepares the current validated v0.8 prototype for battery operation without enabling deep sleep before the final 18650/MAX17048 test.

## Rule for v0.9 preparation

Do not change the validated float truth table or Zigbee endpoint numbering.

Keep:

- endpoint 10: water temperature
- endpoint 11: low float raw contact
- endpoint 12: high float raw contact
- CLOSED = Zigbee ON
- OPEN = Zigbee OFF

## Phase A - safe refactor while still USB powered

- introduce a firmware version constant instead of a hard-coded serial banner
- add compile-time debug logging
- centralize bench/production timing constants
- separate MAX17048 register reading from serial formatting
- return a structured battery telemetry result: voltage, SOC, rate, status, validity
- clamp reported SOC to a sane Zigbee-facing range without hiding raw diagnostic values
- keep DS18B20 power switched from D2
- guarantee DS18B20 DATA is input/high-impedance before any future sleep call
- preserve BOOT >3 s Zigbee factory reset

## Phase B - real battery validation

With the protected 18650 installed:

1. USB-C + battery connected
2. battery-only operation
3. compare MAX17048 VCELL with a multimeter
4. verify SOC plausibility
5. observe CRATE over several minutes
6. inspect STATUS and CONFIG
7. verify GPIO4 / INT electrically HIGH when inactive
8. trigger or configure a useful alert threshold and verify active-low INT

No deep-sleep merge until this passes.

## Phase C - Zigbee battery exposure

After Phase B:

- expose battery percentage through a standard Zigbee battery attribute where supported
- expose battery voltage only if it maps cleanly and remains useful in Zigbee2MQTT
- report battery on periodic wakes, not every loop
- avoid reporting insignificant SOC changes

## Phase D - sleepy operation

Target behavior:

```text
wake
  -> read wake cause
  -> stabilize GPIOs
  -> join/reconnect Zigbee with bounded wait
  -> report relevant float change
  -> optionally measure temperature/battery if due
  -> wait only as long as required for report delivery
  -> configure next GPIO wake levels from current float states
  -> power down DS18B20
  -> sleep
```

## GPIO wake design

Candidate event GPIOs:

- D0 / GPIO0: low float
- D1 / GPIO1: high float
- GPIO4 / MTMS: MAX17048 INT/ALRT

Because external wake is level-sensitive, the firmware must not simply arm the same active level every time. Otherwise a float that remains in that level can immediately wake the ESP again.

The sleep preparation code should derive the next wake level from the current switch state so only the opposite meaningful transition wakes the device.

## Zigbee outage behavior

The current v0.8 code waits indefinitely for `Zigbee.connected()` during startup. That is acceptable for bench validation but unacceptable for a battery device during a coordinator outage.

v0.9 should use a bounded network wait and a controlled retry strategy so an unavailable Zigbee network cannot drain the cell continuously.

## Initial production timing candidates

These are starting points for measurement, not final values:

- temperature wake/report: 30-60 minutes
- battery report: piggyback on temperature wake or every few hours
- float events: event-driven
- debug MAX17048 periodic loop: disabled in production

## Bench validation - 2026-08-31

First flash of `v0.9-prep` completed successfully after the GitHub Actions build passed.

Validated behavior:

- existing Zigbee pairing survived the normal flash
- Zigbee reconnected successfully without re-pairing
- DS18B20 reported 24.00 C correctly
- both float switches transitioned correctly with the new debounce logic
- MAX17048 responded at I2C address `0x36` with VERSION `0x0012`
- STATUS read `0x00`
- CONFIG read `0x971C`, with `CONFIG.ALRT` clear

### MAX17048 alert-line wiring correction

The first bench wiring accidentally connected XIAO GPIO4 / MTMS to the MAX17048 `QSTRT` pin rather than the `INT/ALRT` output. This explained why GPIO4 remained LOW even though STATUS had no alert flags and CONFIG.ALRT was clear.

Corrected wiring:

```text
XIAO GPIO4 / MTMS <--- MAX17048 INT/ALRT
```

`QSTRT` is not connected to GPIO4 and is not used by the firmware.

After moving the wire to `INT/ALRT`, the diagnostic became coherent:

```text
MAX17048 INT: HIGH (inactive)
MAX17048 STATUS=0x00 | no alert cause flags
MAX17048 CONFIG=0x971C | ALRT=clear
MAX17048 INT after acknowledge: HIGH (inactive)
GPIO4 / MAX17048 INT final: HIGH (inactive)
```

This confirms that the firmware mask `MAX17048_CONFIG_ALRT = 0x0020` is consistent with the current 16-bit register read/write representation. Do not change it to `0x2000`.

Battery telemetry values observed while the intended protected 18650 setup is not validated are diagnostic only. Raw SOC may temporarily exceed 100%; any future Zigbee-facing battery percentage should be clamped to 0-100 while preserving the raw value for debug logs.

## Acceptance criteria before merge to main

- builds in GitHub Actions and locally with PlatformIO
- existing Zigbee pairing survives a normal flash
- both float states still report correctly
- temperature still reports correctly
- battery telemetry validated against real hardware
- no infinite Zigbee-connected wait in battery mode
- measured sleep current documented
- repeated float transition test does not cause wake loops
- Home Assistant refill logic still receives the same raw float semantics
