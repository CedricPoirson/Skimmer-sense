# SkimmerSense v0.9 firmware status

This branch now contains the validated deep-sleep / anti-wave implementation for the XIAO ESP32-C6 prototype.

## Stable interface contract

Do not change these semantics without coordinating the Home Assistant automation:

- endpoint 10: water temperature
- endpoint 11: low float raw contact
- endpoint 12: high float raw contact
- CLOSED = Zigbee ON
- OPEN = Zigbee OFF

Float truth table:

- ON + ON = below low level / refill request
- OFF + ON = between low and high / continue refill
- OFF + OFF = high level / stop refill
- ON + OFF = impossible/fault state

Battery telemetry is currently local through MAX17048/serial diagnostics; Zigbee Power Configuration setup/reporting is disabled on this stack.

## Hardware

- Seeed XIAO ESP32-C6
- D0 / GPIO0: LOW float
- D1 / GPIO1: HIGH float
- D2: switched DS18B20 power
- D3: DS18B20 data
- D4 / GPIO22: MAX17048 SDA
- D5 / GPIO23: MAX17048 SCL
- GPIO4 / MTMS: MAX17048 INT/ALRT

The earlier GPIO4/QSTRT wiring mistake was corrected. With GPIO4 connected to the actual INT/ALRT output, the inactive alert line is HIGH and the MAX17048 registers are coherent.

## Zigbee reporting workaround

The current Arduino-ESP32 / ZBOSS stack is not safe for normal runtime attribute mutation/reporting in this firmware.

Validated failure modes:

- runtime `setTemperature()` can synchronously return OK, then ZBOSS crashes asynchronously in automatic reporting (`zb_zcl_get_next_reporting_info` / `zb_zcl_report_attr`)
- explicit Power Configuration `BatteryPercentageRemaining` report asserts in `esp_zigbee_zcl_command.c:263`
- the battery assertion also occurs when the report is fully zero-initialized and addressed directly to coordinator `0x0000` endpoint `1`, so the binding table is not the cause
- `ZigbeeTempSensor::setPowerSource(...)` also causes a reproducible ZBOSS crash in the current firmware configuration

Validated safe pattern:

1. wake and read real sensors before `Zigbee.begin()`
2. preload temperature and float states into endpoint cluster lists before starting Zigbee
3. reconnect Zigbee with a bounded wait
4. send fully zero-initialized explicit reports for temperature and both floats only
5. keep Zigbee Power Configuration setup disabled
6. never explicitly report the battery on this stack
7. avoid runtime Zigbee attribute mutation after startup
8. deep sleep

MAX17048 monitoring remains active locally: VCELL, raw SOC and INT/ALRT diagnostics are still read by the firmware.

## Anti-wave state machine

RTC-retained states:

```text
NORMAL
  LOW closes
    -> LOW_PENDING

LOW_PENDING
  start 5-minute confirmation
  watch LOW for reopening

  LOW reopens before confirmation expires
    -> immediate GPIO wake
    -> reject as wave/bather motion -> NORMAL

  timer expires after LOW remained CLOSED continuously
  + HIGH is CLOSED
    -> publish ON/ON -> WAIT_HIGH

  LOW is CLOSED + HIGH is OPEN
    -> publish impossible/fault state -> NORMAL

WAIT_HIGH
  LOW transitions are ignored
  HIGH opens
    -> immediate GPIO wake
    -> publish final float states -> NORMAL
```

In `NORMAL`, `LOW=CLOSED / HIGH=OPEN` is also treated immediately as an impossible/fault state and does not start `LOW_PENDING`.

A final pre-sleep guard handles a HIGH opening while Zigbee is still awake: the firmware schedules a 1-second timer-only resample instead of risking a missed edge until the fallback timer.

## Hardware validation completed

Validated on the real prototype:

- existing Zigbee pairing survives normal flashing
- DS18B20 reads correctly
- LOW and HIGH float raw states report correctly
- MAX17048 responds at `0x36` with VERSION `0x0012`
- raw MAX17048 SOC can exceed 100%; local diagnostic value is clamped to 0-100% for future Zigbee use
- deep-sleep timer wake works
- LOW wakes the device immediately in NORMAL
- LOW reopening during `LOW_PENDING` wakes immediately and cancels the confirmation
- a full uninterrupted LOW confirmation enters `WAIT_HIGH` and publishes ON/ON
- LOW transitions do not wake the device in WAIT_HIGH
- HIGH opening wakes the device immediately in WAIT_HIGH
- final float reports are queued successfully
- device returns to NORMAL after HIGH opens
- `LOW=CLOSED / HIGH=OPEN` fault handling is validated in NORMAL
- repeated temperature/float Zigbee report cycles survive without assertion or Guru Meditation
- GitHub Actions passes for the current branch head

## Production profile

PlatformIO environment:

`seeed_xiao_esp32c6_sleep_zigbee_production`

Current timings:

- NORMAL periodic refresh: 1800 s / 30 min
- LOW confirmation: 300 s / 5 min continuously CLOSED
- WAIT_HIGH fallback: 1800 s / 30 min
- GPIO float events remain event-driven

The 30-minute WAIT_HIGH fallback is intentional because a confirmed low-water request can remain pending for hours until the overnight refill window. HIGH opening still wakes immediately and therefore is not delayed by the fallback timer.

The production build is explicitly labelled `0.9-production` in serial output.
